# [네이버 블로그 자동화 #1] AI 판타지 단편 소설과 에칭 삽화 연재 파이프라인: Gemini, Imagen 3, 그리고 Playwright의 선택

> **부제: AI 멀티모달 창작부터 네이버 스마트에디터 ONE 자동 발행까지의 여정 (1편)**

---

## 1. 프로젝트의 시작: 용돈 벌기와 창작의 자동화

어느 날 문득 *"본업 외에 개발자로서 재미있게 부수적인 가치(용돈이나 포트폴리오)를 만들어낼 수 있는 방법이 없을까?"*라는 생각이 들었습니다. 

평소 판타지 문학과 일러스트에 관심이 많았던 저는, 최근 비약적으로 발전한 생성형 AI를 활용해 **"매일 한 편씩 독특한 세계관의 판타지 단편 소설과 그에 어울리는 고품질 에칭(동판화) 삽화를 연재하는 블로그"**를 기획하게 되었습니다.

국내에서 가장 독자 접근성이 높고 애드포스트 등 수익화 모델이 갖춰진 플랫폼은 단연 **네이버 블로그**였습니다. 하지만 매일 사람이 직접:
1. LLM에 프롬프트를 넣어 소설을 뽑고,
2. 이미지 생성 AI로 삽화를 만들고,
3. 네이버 블로그 스마트에디터에 로그인해 복사/붙여넣기하고,
4. 삽화를 업로드하고 태그를 입력해 발행하는 작업

을 반복하는 것은 며칠 지나지 않아 번아웃을 유발하기 십상이었습니다.

> **"창작과 발행, 백업까지 모든 과정을 사람의 손이 전혀 닿지 않는 완전 자동화 파이프라인으로 구축해보자!"**

그렇게 이 프로젝트가 시작되었습니다.

## 2. AI 멀티모달 파이프라인 설계: Gemini & Imagen 3

단순히 "재미있는 판타지 소설 써줘"라고 LLM에 요청하면 뻔하고 유치한 용사/마왕 이야기가 반복됩니다. 매일 새로운 재미를 주는 연재물이 되려면 **체계적인 프롬프트 엔지니어링과 규격화(Spec)**가 필수적이었습니다.

### (1) 소설 생성 엔진 (Gemini 2.5 Flash)
* **7가지 테마 순환 시스템**:
  * `Theme A`: 신비로운 길드와 고대 장인 (유리공, 방직공, 시계공)
  * `Theme B`: 금기와 잊힌 맹세
  * `Theme C`: 사물에 깃든 기억과 상점
  * `Theme D`: 비현실적인 기상 현상과 자연의 변이
  * `Theme E`: 그림자와 거울, 경계의 영역
  * `Theme F`: 잊힌 도서관과 금서의 파수꾼
  * `Theme G`: 지도에 없는 장소와 천문학
* **서사 규칙 제약**:
  * 1인칭 전지적 시점이 아닌 **'3인칭 관찰자 시점'** 고정
  * 지나치게 밝은 동화풍을 배제하고, 차분하고 서정적인 **다크 아카데미아/환상문학 톤** 유지
  * 호흡이 늘어지지 않도록 공백 포함 1,500자 내외의 밀도 높은 단편 구성

### (2) 삽화 생성 엔진 (Imagen 3)
블로그의 시각적 통일성을 위해 현대적인 디지털 일러스트 대신 **중세 고서의 삽화 같은 펜화/동판화(Etching & Woodcut Engraving)** 스타일을 선택했습니다.

* **Style Anchor**:
  ```text
  Detailed monochrome pen and ink illustration, cross-hatching line art style, 
  etching and woodcut engraving inspired, classic dark fantasy graphic novel art.
  Strictly no solid color fills, parchment-toned background #ece0c6. High contrast.
  ```
* **블로그 배경색과의 완벽한 일치 (`#ece0c6`)**:
  * 초기 테스트 시 AI가 생성한 배경색(`#E9D5B2` 등)이 블로그 스킨 색상과 미세하게 달라 이질감이 발생했습니다.
  * 프롬프트에 명시적으로 헥스 코드 `#ece0c6`를 고정하고, 캔버스를 16:9 와이드로 강제하여 스마트에디터 본문에 삽입되었을 때 완벽한 통일감을 갖추도록 보정했습니다.

## 3. 왜 Selenium이 아닌 Playwright였는가?

콘텐츠 생성 파이프라인이 갖춰진 뒤, 가장 큰 기술적 관건은 **"네이버 블로그 발행 자동화 도구로 무엇을 선택할 것인가?"**였습니다.

과거 웹 자동화의 표준은 Selenium이었으나, 이번 프로젝트에서는 주저 없이 **Playwright**를 선택했습니다. 그 이유는 다음과 같습니다:

| 비교 항목 | Selenium WebDriver | Microsoft Playwright |
| :--- | :--- | :--- |
| **대기 메커니즘** | 명시적 대기(`time.sleep`, `WebDriverWait`) 빈번히 필요 | **Auto-Wait**: 엘리먼트가 조작 가능할 때까지 자동 대기 |
| **복잡한 DOM/SPA 지원** | React 기반 스마트에디터 ONE의 동적 렌더링 추적에 취약 | 가상 DOM 및 비동기 이벤트에 대한 견고한 셀렉터 엔진 |
| **세션 유지 관리** | 브라우저 프로필 설정이 번거롭고 크래시 빈번 | `userDataDir` 영속화 및 `storageState` 추출이 네이티브 지원 |
| **실행 속도 및 안정성** | HTTP JSON-Wire 프로토콜 오버헤드 존재 | CDP(Chrome DevTools Protocol) 직접 통신으로 압도적 반응 속도 |

특히 네이버의 **스마트에디터 ONE**은 단순 HTML 폼이 아니라 React 컴포넌트로 구성된 복잡한 리치 텍스트 에디터입니다. 클릭 타이밍이 100ms만 어긋나도 툴바가 닫히거나 포커스가 풀리는데, Playwright의 **Actionability Check(클릭 가능할 때까지 엘리먼트의 가시성, 애니메이션 완료, 안정 상태를 자동 확인)** 기능 덕분에 스크립트의 신뢰도를 극대화할 수 있었습니다.

## 4. 첫 번째 발행 파이프라인 구축: 로컬 세션 영속화

네이버와 같은 대형 플랫폼의 자동화에서 가장 큰 장벽은 **자동 로그인 차단과 캡차(CAPTCHA)**입니다. 매번 스크립트가 아이디와 비밀번호를 타이핑하면 즉시 비정상 로그인으로 탐지됩니다.

이를 해결하기 위해 **로컬 브라우저 프로필 영속화 패턴**을 적용했습니다:

```python
# chrome_profile 디렉터리를 생성하여 실제 사용자의 브라우저 세션을 그대로 보존
context = await playwright.chromium.launch_persistent_context(
    user_data_dir="./chrome_profile",
    headless=False,  # 초기 1회 로그인 시 사람이 직접 2단계 인증 수행
    args=[
        "--disable-blink-features=AutomationControlled", # webdriver 감지 우회
        "--start-maximized"
    ]
)
```

1. 최초 1회만 GUI 브라우저를 띄워 수동으로 로그인 및 2단계 기기 등록을 완료합니다.
2. 이후 발행 스크립트는 `./chrome_profile`에 저장된 쿠키, 로컬 스토리지, 보안 토큰을 그대로 재사용하므로, **캡차 유발 없이 즉시 로그인된 상태로 스마트에디터에 진입**할 수 있습니다.
