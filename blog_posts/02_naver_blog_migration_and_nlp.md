## 1. 인트로: 순탄할 줄 알았던 70편 대량 마이그레이션

1편에서는 LLM과 이미지 생성 AI를 연결하고 Playwright로 네이버 블로그에 새 글을 자동으로 발행하는 기본 파이프라인을 구축했습니다. 매일 한 편씩 정해진 시간에 글이 올라가는 것을 보며 안도했습니다.

하지만 블로그 카테고리를 열어본 순간 새로운 고민이 시작되었습니다. **"자동화 시스템을 구축하기 전에 수동으로 올려두었던 기존 70편의 글들은 어떡하지?"**

기존 글들은 태그가 전혀 달려 있지 않았고, 본문 글자 크기나 폰트, 색상도 제각각이어서 블로그의 통일성을 해치고 있었습니다.

> "기존 70편의 글을 읽어서 제목에 어울리는 핵심 키워드 태그를 자동으로 추출해 달아주고, 본문 폰트와 서식을 깔끔하게 일괄 변경하는 마이그레이션 스크립트를 만들자!"

가벼운 마음으로 시작한 이 작업은, 그러나 예상치 못한 브라우저 자동화의 수많은 엣지 케이스와 기술적 벽을 마주하게 만들었습니다.

## 2. 복병 1. 네이버 블로그의 '2페이지 저주'와 iframe의 늪

### 문제 상황
가장 먼저 시도한 방식은 직관적인 Playwright 브라우저 UI 조작이었습니다:
1. 블로그 글 목록 페이지로 이동한다.
2. 1페이지의 글들을 순회하며 수정한 뒤 저장한다.
3. 하단의 `[2]`, `[3]` 페이지네이션 버튼을 클릭해 다음 페이지로 넘어간다.

그런데 이상하게도 **스크립트가 2페이지까지만 작업을 수행하고 3페이지부터는 페이지 넘김을 인지하지 못한 채 무한 대기 상태에 빠지거나 멈추는 현상**이 지속되었습니다.

### 원인 분석
네이버 블로그는 데스크톱 웹 환경에서 전통적인 **중첩 `iframe` 구조(`mainFrame`)**를 사용합니다. 
* 겉보기에는 단일 URL이지만, 실제 콘텐츠와 페이지네이션은 내부 iframe 안에서 비동기 AJAX로 렌더링됩니다.
* 브라우저 자동화 도구가 페이지 번호를 클릭했을 때, 네트워크 응답 지연과 SPA 스타일의 DOM 재렌더링 타이밍이 어긋나면서 `page.wait_for_selector()`가 타임아웃을 일으키거나 이전 페이지의 캐시된 DOM을 재참조하는 'Stale Element' 문제가 발생했습니다.
* 게다가 70편의 글 목록을 브라우저 렌더링 엔진으로 일일이 페이지를 넘겨가며 탐색하는 것은 **목록 탐색에만 2분 이상이 소요될 정도로 비효율적**이었습니다.

### 해결책: UI 크롤링을 버리고 순수 HTTP 리버스 엔지니어링으로 전환

"목록을 수집하는 데 굳이 무거운 크롬 브라우저를 띄워서 페이지네이션 버튼을 누를 필요가 있을까?"

네이버 블로그의 네트워크 패킷을 분석하여, 카테고리별 글 목록을 반환하는 경량 비동기 엔드포인트를 찾아냈습니다.

```python
# [개선 전] 무거운 Playwright 브라우저로 클릭하며 페이지 넘김 (불안정, 2분 이상 소요)
await page.frame_locator("#mainFrame").locator(".pagination a.page").click()

# [개선 후] 순수 HTTP GET 요청으로 비동기 병렬 수집 (안정성 100%, 2.1초 소요)
async def fetch_category_posts_fast(blog_id: str, category_no: int, total_pages: int = 15):

        tasks = [
            client.get(
                f"https://blog.naver.com/PostTitleListAsync.naver?blogId={blog_id}&categoryNo={category_no}&currentPage={p}"
            )
            for p in range(1, total_pages + 1)
        ]
        responses = await asyncio.gather(*tasks)
        # logNo, title, post_date 즉시 파싱
```

* **결과**: 브라우저 UI 페이지네이션 클릭 로직을 완전히 제거하고 순수 HTTP 요청으로 전환한 결과, 70편 전체의 글 번호(`logNo`)와 제목, 작성일을 수집하는 데 걸린 시간이 **2분 이상(간헐적 실패) $\rightarrow$ 2.1초(성공률 100%)로 약 60배 단축**되었습니다.

## 3. 복병 2. 한글 형태소의 배신: `#기억을`, `#거래하는`은 태그가 될 수 없다

기존 글들에 태그를 달아주기 위해 처음에는 제목 문자열을 단순히 공백으로 분리(`split`)한 뒤 불용어를 제거하는 간단한 방식을 사용했습니다. 

그 결과 나온 태그 목록은 당혹스러웠습니다:
```text
입력 제목: "기억을 거래하는 신비한 은빛 상점"
추출된 태그: ['#기억을', '#거래하는', '#신비한', '#은빛', '#상점']
```

`#기억을`, `#거래하는`처럼 목적격 조사나 활용형 동사/형용사가 그대로 태그가 되어 있었습니다. 블로그 검색 엔진 최적화(SEO) 관점에서 이런 태그는 아무런 가치가 없습니다.

### 한국어 교착어(Agglutinative Language)의 난제
한국어는 어간에 조사와 어미가 결합하는 교착어입니다. 완벽한 형태소 분석을 위해서는 `KoNLPy`(Mecab, Okt 등)를 사용하는 것이 일반적입니다. 

하지만 실제 운영 환경에서 KoNLPy는 치명적인 단점이 있었습니다:
1. **무거운 의존성**: C/C++ 빌드 도구와 Java JVM 환경이 필수로 요구되어, 경량 컨테이너나 GitHub Actions 배포 시 빌드 크기가 수백 MB로 비대해집니다.
2. **단순 조사 제거의 함정**: `이/가/을/를` 같은 조사를 무작정 `replace`하거나 잘라내면 `이름` $\rightarrow$ `름`, `과수원` $\rightarrow$ `수원`처럼 단어의 원형이 파괴됩니다.

### 해결책: 정규식 후방 탐색(Positive Lookbehind) 기반 경량 휴리스틱 엔진

외부 의존성 없이 순수 파이썬의 `re` 모듈만으로 교착어의 어미/조사를 정밀 분리하는 **경량 한글 휴리스틱 태거**를 직접 설계했습니다.

```python
# 1. 동사/활용형 어미 제거 정규식
VERB_STRIP_REGEX = re.compile(
    r'(?:하다|하는|하며|하고|했던|하여|되는|된|되며|되고|위한|통한|따른)$'
)

# 2. 관형사형 형용사 필터
ADJ_STRIP_REGEX = re.compile(
    r'(?:있는|없는|같은|어떤|모든|새로운|깊은|높은|밝은|어두운|신비한|거대한|작은|따뜻한|차가운)$'
)

# 3. 단어 원형 파괴를 방지하는 후방 탐색(Positive Lookbehind) 조사 제거
# 앞 글자가 한글 완성형 음절이고, 최소 2음절 이상인 경우에만 말미의 조사를 제거
JOSA_STRIP_REGEX = re.compile(
    r'(?<=[가-힣]{2})(?:에서|에게|으로|로|의|과|와|을|를|은|는|이|가|도)$'
)
```

이 규칙을 파이프라인으로 연결하자 결과가 획기적으로 개선되었습니다:
```text
입력 제목: "기억을 거래하는 신비한 은빛 상점"
[1] 조사 제거: '기억을' -> '기억'
[2] 동사 어미 제거: '거래하는' -> '거래'
[3] 관형사 필터링: '신비한' -> 제거
[4] 명사 수집: '은빛', '상점'
최종 생성 태그: ['#기억', '#거래', '#은빛', '#상점', '#판타지소설']
```
JVM이나 무거운 형태소 사전 없이도 단 **0.001초 만에 깔끔한 고품질 SEO 키워드**를 추출할 수 있게 되었습니다.

## 4. 복병 3. 스마트에디터 ONE 서식 제어 해킹: "왜 본문 스타일이 안 바뀌지?"

기존 글들의 서식을 통일하기 위해 네이버 스마트에디터 ONE의 글 수정 페이지로 진입했습니다. 우리의 목표는 단순했습니다:
1. 본문 전체 선택
2. 폰트를 **'기본서체'**로 변경
3. 글씨 크기를 **15pt**로 변경
4. 글씨 색상을 **통일된 다크 그레이**로 변경

하지만 스마트에디터 ONE은 브라우저 표준 `textarea`나 단순 `contenteditable` 영역이 아닌, **수많은 React 컴포넌트와 커스텀 블록들의 결합체**였습니다.

### 난관 1: `Control+A` 전체 선택의 함정
페이지 전체에서 `page.keyboard.press("Control+A")`를 누르면, 에디터 본문뿐만 아니라 상단 툴바, 제목 입력란, 사이드 패널까지 전체 웹페이지가 파랗게 블록 지정되며 에디터 내부 포커스가 완전히 풀려버렸습니다.

* **해결**: 본문 컴포넌트의 첫 번째 단락 컨테이너(`.se-component-content`)를 찾아 명시적으로 클릭한 후 `Control+A`를 전송하여 오직 '본문 텍스트 블록'만 정확히 하이라이트되도록 가뒀습니다.

### 난관 2: 72색 팔레트 vs 커스텀 HEX 색상의 벽
네이버 에디터 툴바의 글자 색상 버튼을 누르면 기본적으로 72가지 고정 색상 팔레트만 뜹니다. 만약 블로그 브랜딩을 위해 특정한 헥스 컬러(예: `#2c3e50`)를 넣고 싶다면 어떻게 해야 할까요?

DOM 트리를 집요하게 분석한 결과, 팔레트 하단에 숨겨진 구조를 찾아냈습니다:
1. 팔레트 하단의 '더보기(컬러피커)' 버튼(`.se-color-picker-more-button`)을 클릭
2. 숨겨진 HEX 입력 필드(`input.se-selected-color-hex`)가 활성화됨
3. 기존 값을 지우고 원하는 HEX 코드를 입력한 뒤 `Enter` 키 전송

이를 바탕으로 **2단계 적응형 컬러 인젝터**를 구현했습니다:

```python
async def apply_font_color(page: Page, hex_color: str):
    # 1. 글자 색상 툴바 열기
    await page.locator("button[data-name='color']").click()
    
    # 2. 72개 기본 팔레트에 일치하는 색상이 있으면 1클릭으로 적용
    palette_btn = page.locator(f"button.se-color-palette-btn[data-color='{hex_color.lower()}']")
    if await palette_btn.count() > 0:
        await palette_btn.first.click()
        return
        
    # 3. 커스텀 HEX인 경우 더보기 피커를 열어 인풋에 주입
    more_btn = page.locator(".se-color-picker-more-button")
    await more_btn.click()
    hex_input = page.locator("input.se-selected-color-hex")
    await hex_input.fill(hex_color.lstrip("#"))
    await hex_input.press("Enter")
```

이 로직을 완성함으로써, 70편의 글 본문이 나눔고딕이든 돋움이든 어떤 폰트로 흩어져 있었든 간에, 단 한 번의 명령어로 **모든 글의 폰트, 크기, 정렬, 줄간격, 색상을 완벽하게 일괄 통일**할 수 있게 되었습니다.

## 5. 복병 4. 데이터 비대화와 유실 방지: 월별 파티셔닝과 3단계 방어벽

글 수가 늘어나면서 또 다른 현실적인 문제가 발생했습니다.

1. **`history.json`의 비대화**: 단일 JSON 파일에 모든 포스팅 로그가 누적되면서 매번 전체 파일을 로드하고 쓰는 디스크 I/O 비용이 증가했습니다.
   - **해결**: `history/{yyyy-mm}.json` 형태로 월별 파티셔닝을 적용했습니다. 스크립트는 오늘 날짜가 속한 이번 달 JSON만 빠르게 확인하고, 과거 데이터는 안전하게 분리 보관됩니다.
2. **외부 저장소(Google Drive) 업로드 실패**: 대용량 이미지와 원고를 구글 드라이브에 아카이빙할 때 네트워크 일시 단절로 실패하는 문제.
   - **해결**: 최대 3회 지수 백오프(Exponential Backoff) 재시도 로직을 적용하고, 3회 모두 실패할 경우 관리자 메일로 에러 로그와 백업 파일을 즉시 발송하는 **3단계 내결함성(Fault Tolerance)** 안전망을 구축했습니다.
3. **보안 분리**: 설정 파일에 하드코딩될 수 있는 개인 이메일, 네이버 계정 정보, 드라이브 경로를 `.env` 환경 변수 우선 주입 구조로 격리했습니다.
