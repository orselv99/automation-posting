# [네이버 블로그 자동화 #3] GitHub Actions와 웹 시뮬레이터로 완성하는 무인(Serverless) 파이프라인: 시크릿 보안, 에러 내결함성, 그리고 [LIVE RUNTIME]

> **부제: 로컬을 떠나 클라우드로: 서버리스 크론, 무노출 보안 아키텍처, 그리고 기술 블로그 임베드를 위한 인터랙티브 샌드박스 개발기 (3편)**

## 1. 인트로: "로컬 PC를 끄고 싶다"

1편에서는 AI 멀티모달 콘텐츠 생성과 Playwright 기반 네이버 스마트에디터 자동 발행 파이프라인을 구축했고, 2편에서는 70편의 기존 글을 마이그레이션하며 겪었던 iframe 비동기 지연, 교착어 정규식 파싱, 에디터 서식 제어 등의 복병들을 해결했습니다.

이제 시스템은 로컬 환경에서 한 치의 오차도 없이 완벽하게 작동했습니다. 하지만 한 가지 중대한 한계가 남아 있었습니다:

> **"매일 아침 글을 올리기 위해 내 컴퓨터를 항상 켜두고 정해진 시간에 스크립트를 실행해야 하는가?"**

진정한 의미의 '완전 자동화'가 되려면, 사람이 여행을 가거나 잠을 자고 있어도 **서버가 알아서 깨어나 글을 짓고, 삽화를 그리고, 블로그에 발행한 뒤 결과를 아카이빙**해야 했습니다.

그렇다고 한 달에 몇 만 원씩 나가는 24시간 클라우드 가상머신(AWS EC2 등)을 띄우는 것은 작은 사이드 프로젝트에 과도한 비용이었습니다. 이에 대한 해답은 **GitHub Actions의 크론(Cron) 스케줄러와 완전 무료 서버리스 컨테이너 환경**이었습니다.

## 2. 난관 1: 클라우드 러너(Headless Linux)에서의 네이버 캡차(CAPTCHA) 방어벽

로컬에서는 `./chrome_profile` 디렉터리에 실제 브라우저 세션을 보존해 두었기 때문에 네이버 로그인이 스무스하게 진행되었습니다. 하지만 GitHub Actions의 가상 러너(Ubuntu Linux) 환경으로 옮겨갔을 때 거대한 방어벽을 마주쳤습니다:

1. **새로운 IP 및 데이터센터 대역 탐지**: GitHub Actions 러너의 IP(Azure 데이터센터)에서 네이버 로그인을 시도하면 보안 시스템이 비정상 로그인으로 간주하고 즉시 캡차나 2단계 휴대폰 인증을 요구합니다.
2. **헤드리스 환경의 한계**: 완전 무인 환경에서는 사람이 직접 캡차 글자를 읽고 타이핑할 수 없습니다.

### 해결책: 세션 컨텍스트(Storage State) 추출 및 시크릿 주입 파이프라인

이 문제를 해결하기 위해 **로컬 인증 기반 세션 토큰 주입 아키텍처**를 설계했습니다:

```text
[로컬 PC (최초 1회)]
  └─ 사람이 직접 브라우저로 2단계 로그인 완료 (신뢰 기기 등록)
  └─ Playwright context.storage_state() 함수로 로그인 쿠키 & 스토리지 토큰 JSON 추출
  └─ Base64 인코딩 후 GitHub Actions Repository Secrets (NAVER_SESSION_STORAGE)에 등록

[GitHub Actions 가상 러너 (매일 자동 실행)]
  └─ Runner 시작 시 Secrets에서 세션 토큰 디코딩 후 브라우저 컨텍스트에 즉시 주입
  └─ context = await browser.new_context(storage_state="session.json")
  └─ 로그인 페이지를 거치지 않고 바로 스마트에디터 글쓰기 URL로 직행! (캡차 0% 회피)
```

이 방식을 통해 원격 서버리스 환경에서도 네이버 보안 시스템을 자극하지 않고 100% 신뢰된 브라우저 세션으로 글을 작성할 수 있었습니다.

## 3. 난관 2: Zero-Leakage 보안 설계 (시크릿 격리와 계층형 로더)

자동화가 고도화될수록 다루어야 하는 민감 정보가 급증했습니다:
* 네이버 계정 정보 (`NAVER_ID`, `NAVER_PW`)
* Google Drive OAuth 2.0 클라이언트 시크릿 및 리프레시 토큰 (`GDRIVE_REFRESH_TOKEN`)
* 시스템 장애 시 알림을 보낼 Gmail SMTP 앱 비밀번호 (`EMAIL_APP_PASSWORD`)
* 개인 수신 이메일 및 로컬 아카이빙 경로

만약 실수로 이 정보가 담긴 설정 파일이 GitHub 공개(Public) 저장소에 커밋된다면 심각한 보안 사고로 이어집니다. 이를 방지하기 위해 **계층형 환경 변수 우선순위 오버라이드 엔진([`config_loader.py`](file:///D:/.repo/.private/artifacts_1/config_loader.py))**을 구축했습니다:

```python
# 1순위: OS 환경 변수 / GitHub Actions Secrets
# 2순위: .env 로컬 파일 (git 추적 제외)
# 3순위: config.json (템플릿 기본값)
def get_env_or_config(key, config_dict, default=""):
    env_val = os.getenv(key)
    if env_val:
        return env_val
    return config_dict.get(key, default)
```

`.gitignore`에 `.env`, `*secret*.json`, `*token*.json`, `chrome_profile/`을 등록하고, 저장소에는 안전한 더미 값만 들어 있는 `.env.example`만 노출되도록 철저히 격리했습니다.

## 4. 난관 3: 멈추지 않는 시스템 - 3단계 내결함성(Fault-Tolerant) 아키텍처

무인 자동화의 핵심은 **"사람이 보고 있지 않아도 장애가 발생했을 때 스스로 복구하거나 안전하게 보고하는 내결함성"**입니다.

네트워크 순단이나 일시적인 API 오류로 전체 파이프라인이 중단되는 것을 방지하기 위해 3단계 안전망을 구축했습니다:

```mermaid
flowchart TD
    A[소설 & 삽화 생성 완료] --> B[스마트에디터 ONE 발행 시도]
    B -->|DOM 대기 & 자동 재시도| C{발행 성공?}
    C -->|성공| D[Google Drive 아카이빙 시도]
    C -->|실패| G[비상 이메일 발송]
    D -->|실패 시 지수 백오프 3회 재시도| E{업로드 성공?}
    E -->|성공| F[history/{yyyy-mm}.json 파티션 기록 및 완료]
    E -->|3회 모두 실패| G[SMTP 비상 알림 발송 + 원고/로그 첨부]
```

1. **1차 방어 (Playwright Auto-Wait)**: 스마트에디터의 컴포넌트 렌더링 지연 시 무작정 에러를 뿜지 않고 대상 엘리먼트가 준비될 때까지 지능적으로 대기.
2. **2차 방어 (지수 백오프 3회 재시도)**: 대용량 이미지 업로드 시 구글 드라이브 API 호출 실패 시 `2초 -> 4초 -> 8초` 대기 후 재시도.
3. **3차 방어 (비상 이메일 SOS)**: 3회 재시도 후에도 최종 실패할 경우, 작성된 소설 원고 텍스트와 이미지 파일, 에러 스택트레이스를 첨부하여 관리자 Gmail로 비상 알림 메일을 전송.

이 3단계 안전망 덕분에 사용자는 "오늘 아침 글이 잘 올라갔을까?"를 매일 불안해하며 확인할 필요가 없어졌습니다.

## 5. 포트폴리오의 화룡점정: `[LIVE RUNTIME]` 인터랙티브 샌드박스 제작기

개발자로서 가장 중요한 순간 중 하나는 **"내가 만든 백엔드/인프라 기술을 이직용 포트폴리오나 기술 블로그 방문자(테크 리더, 면접관)에게 어떻게 효과적으로 보여줄 것인가?"**입니다.

보통의 백엔드/스크립트 프로젝트는 GitHub 저장소 링크와 긴 README 텍스트, 콘솔 캡처 스크린샷 몇 장으로 끝나기 마련입니다. 하지만 바쁜 채용 담당자가 내 저장소를 클론받아 파이썬 가상환경을 만들고, 크롬 브라우저를 깔아서 스크립트를 직접 돌려볼 확률은 거의 0%에 수깝습니다.

> **"블로그의 `[LIVE RUNTIME]` 영역에서, 방문자가 1초 만에 스마트에디터 서식 제어와 한글 형태소 태깅 알고리즘을 직접 만져볼 수 있는 인터랙티브 웹 샌드박스를 만들자!"**

![Live Runtime 샌드박스 구조](file:///D:/.repo/.private/artifacts_1/generated/screenshots/03_smart_editor_view.png)

### 웹 샌드박스 구현 포인트
1. **스마트에디터 ONE 서식 조작기**:
   - 폰트(기본서체, 마루부리, 나눔명조), 폰트 크기(11~28pt), 색상 팔레트 및 커스텀 HEX 피커, 정렬 및 줄간격을 브라우저에서 실시간으로 변경.
   - 우측의 스마트에디터 본문 캔버스에 즉각 렌더링 반영.
2. **한글 형태소/정규식 태그 추출 엔진 포팅**:
   - 파이썬으로 구현했던 `VERB_STRIP_REGEX`, `ADJ_STRIP_REGEX`, `JOSA_STRIP_REGEX` 및 후방 탐색 방어 로직을 순수 JavaScript로 1:1 포팅.
   - 방문자가 임의의 제목을 입력하고 `[태그 추출]`을 누르면, 조사/어미가 잘려 나가며 고품질 태그 칩이 실시간으로 팝업되는 과정을 시각화.
3. **Playwright 액션 로거 시뮬레이터**:
   - 사용자가 서식을 변경할 때마다 실제 Playwright가 클릭하는 셀렉터와 DOM 제어 이벤트(`page.locator(...)`)를 하단 콘솔에 실시간 터미널 스타일로 출력.
4. **70편 연재 소설 아카이브 뷰어**:
   - 실제 발행된 70편의 판타지 소설 데이터와 에칭 삽화(`#ece0c6`)를 클릭 한 번으로 불러올 수 있는 프리셋 탑재.

이 웹 샌드박스는 **GitHub Pages**를 통해 배포되어, 개인 이직 블로그(`https://orselv99.github.io/artifacts/`)의 `[LIVE RUNTIME]` 컨테이너 안에서 완벽하게 단독 실행됩니다.

## 6. 시리즈를 마무리하며: 단순한 매크로와 소프트웨어 엔지니어링의 차이

이 프로젝트는 "용돈이나 벌어볼까?"라는 작은 호기심과 단순한 브라우저 매크로 구상에서 출발했습니다. 

하지만 실제로 문제를 해결해 나가는 과정은 진짜 소프트웨어 엔지니어링의 정수였습니다:
* 무거운 UI 크롤링을 버리고 **네트워크 엔드포인트를 역공학(HTTP Reverse Engineering)**하여 속도를 60배 단축시켰고,
* 무거운 외부 라이브러리 없이 순수 **정규식 후방 탐색 휴리스틱**으로 교착어 형태소의 한계를 극복했으며,
* 복잡한 **리치 텍스트 에디터의 섀도우 컴포넌트 트리와 툴바를 분석**해 완벽한 서식 제어기를 완성했고,
* **서버리스 크론, 계층형 시크릿 보안, 3단계 내결함성 안전망**으로 멈추지 않는 무인 시스템을 구축했습니다.
* 마지막으로 보이지 않는 백엔드 로직을 **방문자가 직접 체험할 수 있는 인터랙티브 웹 런타임**으로 시각화했습니다.

> *"어떤 작은 자동화라도, 마주치는 예외와 기술적 한계를 끝까지 파고들어 견고하게 설계할 때 비로소 진정한 엔지니어링 자산이 된다."*

이 3부작 연재가 웹 자동화, 헤드리스 브라우저 제어, AI 파이프라인 구축을 고민하는 동료 개발자분들께 작은 영감이 되기를 바랍니다. 긴 글 읽어주셔서 감사합니다!
